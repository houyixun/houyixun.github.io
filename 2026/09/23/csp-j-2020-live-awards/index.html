CSP-J 2020「直播获奖」：从动态排名到 601 个计数桶

今天练习了 CSP-J 2020 的「直播获奖」。这道题最值得记住的地方，是选择算法之前，先把数据范围读完整。

看到“不断加入成绩，实时求前若干名的最低分”，我首先想到的是排序和堆。但题目还有一个更关键的条件：成绩是 0～600 的整数，只有 601 种可能。

本文的核心思路： 用计数桶记录每个分数有多少人，再从高分向低分累加，找到覆盖第 K 名的那个分数。

01 · 先明确：我们究竟要查询什么？

题目链接：洛谷 P7072 · CSP-J 2020 直播获奖。

每读入一个新成绩，都要输出此时的获奖分数线。已公布成绩的人数为 i，获奖百分比为 w，计划获奖人数就是：

这里的 ⌊ ⌋ 表示向下取整。将当前所有成绩从高到低排列，第 K 名的成绩就是分数线。

注意，“计划获奖人数”与“实际获奖人数”不一定相等。例如，当前成绩为 600、500、500、200，若计划取前 2 名，分数线就是 500，两个 500 分的选手都获奖，实际获奖人数为 3。

我们只需找出第 K 名的分数，无需逐个标记获奖选手，也无需给并列者重新编号。

02 · 从数据范围选择算法

本题的约束可以概括为：

参数 范围 对算法选择的提示
选手总数 n 最大 100000 每次遍历全部已有选手，代价很高
成绩 score 0～600 的整数 可以直接用数组下标表示分数
获奖百分比 w 1～99 的整数 可以用整数乘除精确计算 K

每次重新排序：重复工作太多

第 i 次插入后，对当前 i 个成绩调用一次 std::sort()，该轮排序的复杂度为 O(i log i)。把所有轮次加起来，总体为 O(n² log n)。

前一轮已经排过的成绩，下一轮又要参与排序。对于 10 万次动态查询，这种做法难以满足时限。

对顶堆：可行，但不是本题最简洁的选择

可以用一个小根堆维护前 K 大成绩，用另一个大根堆维护其余成绩，并随 K 的变化调整两个堆的大小。这是通用的 O(n log n) 解法。

不过，本题的分数范围很小。我们可以省去两个堆的平衡逻辑，直接数一数每个分数出现了几次。

不要把“更简单”理解为“一定更快”。 桶扫描与堆的实际速度取决于实现和数据；600 也不一定小于 log n 对应的操作代价。计数桶的优势在于充分利用值域，写法直接、内存占用小，也容易验证正确性。

03 · 用 601 个桶维护成绩分布

令 counts[s] 表示当前获得 s 分的人数，下标从 0 到 600。

新成绩到来时，只做一次更新：

查询时，从 600 分向 0 分扫描，累计人数。一旦累计人数不少于 K，当前分数就是答案。

以成绩 600、500、500、200、K = 2 为例：

扫描到的分数 该分数人数 累计人数 是否已覆盖第 2 名
600 1 1 否，继续向下
599～501 0 1 否，空桶不改变累计人数
500 2 3 是，分数线为 500

累计人数从 1 直接跳到了 3，这正好包含了分数相同的两名选手。因此，判断条件应当是 >= K，不能写成 == K。

05 · 为什么这个算法一定正确？

每读入一个成绩，就将对应桶加一。因此，处理完前 i 个成绩后，counts[s] 始终准确记录其中 s 分的人数。

从高分向低分扫描，设首次使累计人数达到或超过 K 的分数为 s。此时：

  • 严格高于 s 分的人数小于 K，否则此前就应该停止扫描。
  • 不低于 s 分的人数至少为 K，因为当前累计人数已经达到 K。

所以，第 K 名一定落在 s 分这一组里，分数线就是 s。

又因为 1 ≤ K ≤ i，而所有桶的人数之和恰好为 i，扫描到 0 分之前或恰好在 0 分时，一定能够找到答案。

复杂度应当怎样写？

设最大分数为 U = 600。

  • 单次插入：O(1)，只更新一个桶。
  • 单次查询：O(U + 1)，最多检查 601 个桶。
  • 总时间：O(n(U + 1))，在本题中通常简写为 O(600n)。
  • 额外空间：O(U + 1)，只存储 601 个计数，无需保存完整成绩序列。

在最大数据下，扫描桶的次数不超过 100000 × 601 = 60100000。这是约 6010 万次简单的数组访问、累加和比较；提前找到答案时还会更少。

由于本题的 U 固定，也可以说该算法关于 n 是线性的。但整个程序并不是 O(1)，我们也没有真正维护一份排好序的选手列表。

07 · 几个比“微优化”更值得注意的细节

1. 用整数计算计划获奖人数

这里应当先乘后除。写成 i * (w / 100) 会让括号内的整数除法恒为 0；写成 i / 100 * w 也会提前丢失余数。

浮点数未必能精确表示百分比，在取整边界附近可能造成偏差。本题完全可以使用整数计算，没有必要引入这种风险。

本题中 i * w ≤ 100000 × 99 = 9900000，使用竞赛环境常见的 32 位 int 足够。如果迁移到更大数据范围，应重新检查溢出，并按需使用 1LL * i * w / 100。

2. 数组需要包含 0 分这一桶

分数共有 601 种，因此 MAX_SCORE + 1 个元素就足够。开到 605 也可以，但多开的空间不能替代边界分析。

查询循环应写成 s >= 0。如果漏掉 0 分，全员 0 分时就无法输出答案。

3. 所有桶必须从 0 开始

末尾的 {} 将每个计数初始化为 0。局部普通数组如果不初始化，其元素值是不确定的，后续累加就会出错。

4. 前置递增是风格选择，不是这道题的提速关键

代码统一使用 ++i。对于这里的 int，当表达式返回值未被使用时，++i 和 i++ 通常会生成相同的优化代码。

对某些自定义迭代器，后置递增可能需要保存旧值，因此不需要旧值时习惯使用前置递增是合理的。但这不意味着 i++ 在本题中是性能陷阱。

真正改变可行性的，是减少重复排序、利用有限值域，而不是把递增运算符换一个位置。

08 · 如果分数范围变大，还能怎么做？

计数桶很适合本题，但也有明确的适用边界：如果分数上限变成十亿，每轮遍历整个值域就不再现实。

方法 总时间复杂度 额外空间 适用考虑
每轮重新排序 O(n² log n) O(n) 适合小数据验证思路
有序数组插入 O(n²) O(n) 二分定位后仍可能搬移大量元素
对顶堆 O(n log n) O(n) 值域较大时的通用做法
计数桶 + 倒序扫描 O(n(U + 1)) O(U + 1) 本题值域小，实现最直接
树状数组 + 第 K 小查询 O(n log(U + 1)) O(U + 1) 能按频次查询排名，需实现二进制提升

树状数组在较大值域下更有优势；如果可以预先读入全部成绩，还可以离散化后依次处理。真正无法预读的数据流，则可以考虑对顶堆或支持排名查询的平衡树。

这道题给我的提醒是：先同时观察数据量、值域和查询目标，再选择数据结构。 当我们只关心“第 K 名是多少分”时，记录每个分数的人数，就已经保留了解题所需的全部信息。
